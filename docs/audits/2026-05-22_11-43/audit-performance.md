## PERF-01: Загрузка файлов — полное чтение в память вместо стриминга
- **Статус**: ❌ FAIL
- **Severity**: 🔴
- **Файл**: `src/modules/file-upload/file-upload.service.ts:70`
- **Описание**: `part.toBuffer()` читает весь файл в ОЗУ, затем `writeFile` записывает на диск. Для файлов до 5MB (лимит) это создаёт двойное потребление памяти на каждый загружаемый файл. При 10 одновременных файлах — до 100MB буферов.
- **Рекомендация**: Использовать стриминг — `part.file.pipe()` или `fsAsync.writeFile(fullPath, part.file)` с обработкой ошибок через `finished()`.

## PERF-02: Отклонённые файлы тоже читаются в память
- **Статус**: ❌ FAIL → ✅ FIXED
- **Severity**: 🟡
- **Файл**: `src/modules/file-upload/file-upload.service.ts:59`
- **Описание**: Даже когда MIME-тип не разрешён, вызывается `await part.toBuffer()` перед `return null`. Буфер выделяется, но сразу выбрасывается.
- **Рекомендация**: Убрать `part.toBuffer()` из блока отклонения — достаточно проверить `mimetype` и сразу вернуть `null`.
- **Исправлено**: Да (toBuffer удалён из rejection)

## PERF-03: Короткий TTL кэша профилей в Redis
- **Статус**: ❌ FAIL → ✅ FIXED
- **Severity**: 🟡
- **Файл**: `src/common/auth/auth.service.ts:27,46`
- **Описание**: TTL кэша профилей — 300 секунд (5 минут). При частых запросах это вызывает избыточные походы в БД. Профили редко меняются, могут кэшироваться дольше.
- **Рекомендация**: Увеличить TTL до 3600 (1 час). При updateProfile кэш и так сбрасывается (PERF-04).
- **Исправлено**: Да (TTL 300→3600)

## PERF-04: Инвалидация кэша при updateProfile без write-through
- **Статус**: ❌ FAIL → ✅ FIXED
- **Severity**: 🟢
- **Файл**: `src/modules/profile/profile.service.ts:24-27`
- **Описание**: При обновлении профиля кэш удаляется, но новый профиль не записывается обратно в Redis. Следующий запрос пойдёт в БД, чтобы перезаполнить кэш.
- **Рекомендация**: После `update` записать обновлённый профиль в Redis напрямую: `.set(key, JSON.stringify(updated), 'EX', 3600)`.
- **Исправлено**: Да (write-through cache + TTL 3600)

## PERF-05: Нет индексов на таблице Upload
- **Статус**: ❌ FAIL → ✅ FIXED
- **Severity**: 🟠
- **Файл**: `prisma/schema.prisma:30-42`
- **Описание**: У модели `Upload` только уникальный индекс на `filepath`. Поля `uploaderIp` и `createdAt` не индексированы. При росте таблицы запросы по `uploaderIp` (например, админка или отчёты) будут делать full scan.
- **Рекомендация**: Добавить `@@index([uploaderIp])` и `@@index([createdAt])`.
- **Исправлено**: Да (индексы добавлены)

## PERF-07: BullMQ worker без конфигурации concurrency
- **Статус**: ❌ FAIL → ✅ FIXED
- **Severity**: 🟡
- **Файл**: `src/infrastructure/test-queue/test-queue.processor.ts:5`
- **Описание**: `@Processor('test')` без указания `concurrency`. По умолчанию BullMQ обрабатывает 1 задачу за раз (serial). Даже для тестовой очереди это узкое место.
- **Рекомендация**: Добавить `@Processor('test', { concurrency: 5 })`. Для продакшен-очередей настраивать под характер задач.
- **Исправлено**: Да (concurrency: 5)

## PERF-08: Redis lazyConnect — задержка на первом запросе
- **Статус**: ✅ PASS (ACCEPTED)
- **Severity**: 🟢
- **Файл**: `src/common/redis/redis.service.ts:26`
- **Описание**: `lazyConnect: true` — Redis подключается при первом вызове. Первый запрос может быть медленнее на время handshake (1-5ms).
- **Рекомендация**: Не критично. Можно добавить вызов `await this.client.connect()` в `onModuleInit` для предварительного подключения.

## PERF-09: Пул соединений Prisma = 10 — может быть узким
- **Статус**: ✅ PASS (ACCEPTED)
- **Severity**: 🟡
- **Файл**: `src/common/prisma/prisma.service.ts:33`
- **Описание**: `max: 10` соединений в пуле. При одновременной обработке нескольких GraphQL-запросов + subscription + health checks пул может исчерпаться, вызывая ожидание соединения.
- **Рекомендация**: Увеличить до 20-25, особенно если планируется рост нагрузки. Мониторить через `pg_stat_activity`.

## PERF-10: child_process.exec в backup.ts — буферизация в память
- **Статус**: ⏸ ACCEPTED
- **Severity**: 🟡
- **Файл**: `src/db-backup-tool/backup.ts:104`
- **Описание**: `child_process.exec()` буферизирует весь stdout/stderr в памяти. Для pg_dump больших БД (гигабайты) это может привести к OOM. Shell-пайп (`| gzip`) требует exec — это оправдано.
- **Рекомендация**: Использовать `spawn` с pipe-стримом для gzip вместо shell-пайпа, чтобы избежать двойной буферизации. Но для MVP — ACCEPTED.

## PERF-11: JSON.stringify + JSON.parse для truncation в логах
- **Статус**: ✅ PASS (ACCEPTED)
- **Severity**: 🟢
- **Файл**: `src/common/logger/gql-logging.interceptor.ts:49-51`
- **Описание**: Для обрезки больших объектов логгер делает `JSON.stringify` полного ответа, обрезает строку, затем `JSON.parse`. Неэффективно для больших ответов (>4KB).
- **Рекомендация**: Пропускать truncation если `jsonStr.length <= maxBytes`. Уже частично решено проверкой длины.
